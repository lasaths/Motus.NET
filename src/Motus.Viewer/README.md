# Motus.Viewer — Blazor WebAssembly Bamboo Arm Viewer

**This is the sole Motus bamboo viewer.** The standalone HTML preview under
`/workspace/bamboo-viewer` (and any sibling Grasshopper PR HTML assets) is
**retired as a product viewer** — kept only as a visual/UX reference. Do not
treat that folder as the shipping UI.

A Blazor WebAssembly app that runs Motus.NET kinematics, collision checking, and
task validation in the browser. The `/bamboo` page ports the look and UX of the
old ICD/LIS HTML preview (pole hang, parallel jaws, θ axes, task cards, scrub)
while Motus.NET remains the source of truth for joint state, tasks, and collision.

## Architecture

```
Browser (WebAssembly)
├── Blazor UI (BambooViewer.razor)       # sliders, tasks, play/scrub, stop-on-hit
├── Motus.NET C# (WASM)
│   ├── bamboo_icd.urdf                  # hung arm: kinematics + collision boxes (generated)
│   ├── BambooIcdCell                    # robot model + CollisionScene (pole, strut, ground, mount)
│   ├── RobotMeshCollisionChecker        # exact narrow phase, FindContacts → named hit pairs
│   ├── BambooMotionScan                 # samples the motion, first hit / last clear sample
│   └── BambooIcdMotion / BambooIcdIk    # ICD planar IK + motion keys (+ Motus IInverseKinematics)
└── Three.js (js/viewer.js)              # draw only, from the cell description C# hands it
```

**Key principle:** Three.js only draws. Joint angles, gripper openings, the strut
pose (Motus FK), task frames, and collision status are computed in C# and pushed via
`initThreeJs(cell)` / `setBambooPose` / `setBambooFrames`. There is no JS collision code.

## Frame convention

| Layer | Up axis | Notes |
|-------|---------|-------|
| Three.js viewer | **Y-up** | pole at `y = 0.40`, segments along local −Y |
| Motus.NET | **Z-up** | `Motus = Rx(+90°) · viewer`, i.e. viewer `(x, y, z)` → Motus `(x, −z, y)` |

`bamboo_icd.urdf` (generated by `tools/bamboo/gen_bamboo_urdf.py`) hangs the arm from a
fixed `pole_hang` joint (`xyz 0 0 0.40`, `rpy π/2 0 π/2`) so every URDF link frame *is* the
matching Three.js group (mount, j1…j5, jaw). Tests assert Motus FK == the drawn chain to 1e-9 m.
Task planes → Motus TCP frames: `BambooIcdMotion.PlaneToMotusFrame` (rotation `Rx(90° + pitch)`).

## Collision (what Motus checks)

- **Robot:** the URDF's own `<collision>` boxes per link — θ housings, link tubes, neck,
  R-grip carriage/rail/jaw plates (plates moved to the current gR opening). viewer.js builds its
  boxes from the same list, so drawn == collided.
- **Scene (`CollisionScene`):** support pole (Three.js-tessellated cylinder mesh), strut (mesh),
  ground slab (box, top at y = 0), fixed mount parts (base tube, L-grip body/rail/jaws at gL).
- **Self:** every part pair except directly-jointed links (`selfCollisionMinLinkGap = 2`).
- **Strut physics:** it rests where the pick object lies (grasp plane un-nudged origin);
  is captured at its real jaw-local offset when the jaws close (attached body, checked against
  scene + all links); stays where released. Only the two R-grip jaw plates may touch it while
  gripping. Closed jaws that would not enclose it → "grasp misses strut", it stays on the ground.
- **Narrow phase:** exact OBB–OBB (SAT), triangle–OBB (SAT), closest-point sphere–triangle,
  mesh vs half-space. (Replaces the old sphere-cloud box test that over-reported by up to a
  half-extent and the 1 cm vertex-sphere mesh test.)
- **Path:** `BambooMotionScan` samples the motion (≤ 0.5° per joint per check), stops at the
  first Motus contact; play and scrub park on the last clear sample and tint the parts Motus names.
- Allowed contacts: θ1 housing ↔ base tube (the θ1 journal); R-grip jaw plates ↔ strut while gripping.

Known colliding nudge: pick `grasp` = **−1.5 mm** (default neck↔strut clearance is 1.0 mm)
→ "Motus stop · Grasp · neck ↔ strut". Place `release` = −10 mm → held strut ↔ ground.

## Run

```bash
cd src/Motus.Viewer
dotnet run --urls http://127.0.0.1:5268
```

Open `http://127.0.0.1:5268/bamboo` (single strut pick/place) or
`http://127.0.0.1:5268/bamboo-truss` (material store → two-triangle truss).

### `/bamboo-truss`: grounded, base-swapping true IK

- **Truss:** vertical-plane bridge **lower chord** A–B–D, edge canes `BambooTrussLayout.StrutLength` = **0.5 m**:
  baseL `/` (A→B) + baseR `_` (B→D). Two 14 mm canes cannot share node B, so baseR is lashed 16 mm beside
  baseL (`LashDz`); A and D sit over anchor posts on pads. No hang rod (`IncludePole = false`), no floating mount.
- **Grounded start:** the L-grip starts clamped on anchor **stake S1** (14 mm post on its own pad beside the
  feed rail; clamp frame `StartBase`, heading −66.2°, chosen by an offline reach + Motus clearance search).
  The feed cane lies on a narrow **feed rail** (`store-rack`) so the open R jaws straddle it (a cane flat on
  the ground leaves ~3 mm under the plates; 0.5 mm seat gap because Motus counts resting contact as a hit).
- **Invariant:** at every instant ≥ 1 gripper is clamped on a real fixed object (a stake, or a cane fixed at
  both ends) and is the IK base (`MotionKey.Base / BaseWorld / BaseOn`). The other gripper moves only by
  joint IK (`BambooGripKinematics.SolveGrip`, damped least squares on full FK, 5 constraints: grasp centre on
  the object axis + slot axis along it). Grips are accepted within **0.5 mm / 0.5°** (achieved ≈ 1e-7 mm).
  A base swap happens at rest: the newly clamped gripper's FK frame becomes the base, then the old one opens.
- **Phases:** `start:Park` → per member `Transit/Approach/Grasp/Close` (R on the feed cane) → `Lift` (along the
  jaw's own +Y) → `Carry` (RRT-Connect, Motus-checked) → `Align/Lower` → `Open` (cane released exactly where
  the jaw put it) → `Retreat`; then `walk`: R clamps double-fixed baseL → **base L→R** → L opens and slides
  up off S1's free top → over and down onto stake S2 → L closes → **base R→L** → R opens, retreats and
  re-grips baseL further along. The L-grip is a closed clamp (a cane cannot leave it sideways), so it only
  moves between supports with free ends (stakes); the open-slot R-grip clamps canes.
- **Collision:** Motus.NET for every link, both grippers, every mount part (now checked against the
  environment, not only self), the held cane, pads, posts, stakes, rail, placed canes (at their real
  released poses) and self. The only allowed touches are a gripper's jaw plates on what it clamps.
  Cylinder meshes are subdivided along their length (~25 mm rings) so the BVH works for long canes.
- **Scan:** `BambooTrussScan` re-derives everything from the keys (base frame, FK of both grippers, held
  offset from the Close key, released pose from the Open key) and checks every ≤ 0.5° step.
- **Viewer:** the mount is drawn at its full FK pose; an amber ring + label marks the clamped base
  ("L clamped on stake-S1", "R clamped on placed-baseL").
- **Play:** `BambooTrussPlayback` dwells 0.35 s at the end of every block (last key of a same-label run),
  keeps time as a double, and never runs past the Motus-verified frontier (time-boxed `StepFor` scan).
- **WASM:** live planning takes ≈ 7 s desktop but minutes in interpreted WASM and cannot yield inside a
  phase, so the page loads the default plan from `Services/BambooTrussDefaultPlan.json` (embedded; keyed by
  `LayoutFingerprint`, falls back to live planning if stale). A test requires it to be byte-identical to
  live planning; regenerate with `BAMBOO_TRUSS_WRITE_PLAN=1 dotnet test --filter ShippedDefaultPlan`.
- **Not built:** sep / diags (the arm works from stakes beside the chord; only the lower chord is placed).

## What still differs from the HTML preview

- The planner keeps the HTML's point-model floor heuristics only as IK-branch *preferences*
  (`FloorPenalty`); they never veto a path. Collision verdicts are Motus-only.
- ICD planar IK for play lives in `BambooIcdMotion` (C#); `BambooIcdIk` exposes it as a Motus
  `IInverseKinematics` so `TaskPathValidator` can validate bamboo task paths.
- The grasp plane cannot be driven much lower than −1.5 mm: at −2 mm it is outside the arm's reach.
- Blazor template Counter/Weather pages were removed; Bootstrap assets may remain unused.
