# Motus.Viewer — Blazor WebAssembly Bamboo Arm Viewer

**This is the sole Motus bamboo viewer.** The standalone HTML preview under
`/workspace/bamboo-viewer` (and any sibling Grasshopper PR HTML assets) is
**retired as a product viewer** — kept only as a visual/UX reference. Do not
treat that folder as the shipping UI.

A Blazor WebAssembly app that runs Motus.NET kinematics, collision checking, and
task validation in the browser. The `/bamboo` page ports the look and UX of the
old ICD/LIS HTML preview (pole hang, parallel jaws, θ axes, task cards, scrub)
while Motus.NET remains the source of truth for joint state, tasks, and collision.

## Architecture

```
Browser (WebAssembly)
├── Blazor UI (BambooViewer.razor)       # sliders, tasks, play/scrub, stop-on-hit
├── Motus.NET C# (WASM)
│   ├── bamboo_icd.urdf                  # hung arm: kinematics + collision boxes (generated)
│   ├── BambooIcdCell                    # robot model + CollisionScene (pole, strut, ground, mount)
│   ├── RobotMeshCollisionChecker        # exact narrow phase, FindContacts → named hit pairs
│   ├── BambooMotionScan                 # samples the motion, first hit / last clear sample
│   └── BambooIcdMotion / BambooIcdIk    # ICD planar IK + motion keys (+ Motus IInverseKinematics)
└── Three.js (js/viewer.js)              # draw only, from the cell description C# hands it
```

**Key principle:** Three.js only draws. Joint angles, gripper openings, the strut
pose (Motus FK), task frames, and collision status are computed in C# and pushed via
`initThreeJs(cell)` / `setBambooPose` / `setBambooFrames`. There is no JS collision code.

## Frame convention

| Layer | Up axis | Notes |
|-------|---------|-------|
| Three.js viewer | **Y-up** | pole at `y = 0.40`, segments along local −Y |
| Motus.NET | **Z-up** | `Motus = Rx(+90°) · viewer`, i.e. viewer `(x, y, z)` → Motus `(x, −z, y)` |

`bamboo_icd.urdf` (generated by `tools/bamboo/gen_bamboo_urdf.py`) hangs the arm from a
fixed `pole_hang` joint (`xyz 0 0 0.40`, `rpy π/2 0 π/2`) so every URDF link frame *is* the
matching Three.js group (mount, j1…j5, jaw). Tests assert Motus FK == the drawn chain to 1e-9 m.
Task planes → Motus TCP frames: `BambooIcdMotion.PlaneToMotusFrame` (rotation `Rx(90° + pitch)`).

## Collision (what Motus checks)

- **Robot:** the URDF's own `<collision>` boxes per link — θ housings, link tubes, neck,
  R-grip carriage/rail/jaw plates (plates moved to the current gR opening). viewer.js builds its
  boxes from the same list, so drawn == collided.
- **Scene (`CollisionScene`):** support pole (Three.js-tessellated cylinder mesh), strut (mesh),
  ground slab (box, top at y = 0), fixed mount parts (base tube, L-grip body/rail/jaws at gL).
- **Self:** every part pair except directly-jointed links (`selfCollisionMinLinkGap = 2`).
- **Strut physics:** it rests where the pick object lies (grasp plane un-nudged origin);
  is captured at its real jaw-local offset when the jaws close (attached body, checked against
  scene + all links); stays where released. Only the two R-grip jaw plates may touch it while
  gripping. Closed jaws that would not enclose it → "grasp misses strut", it stays on the ground.
- **Narrow phase:** exact OBB–OBB (SAT), triangle–OBB (SAT), closest-point sphere–triangle,
  mesh vs half-space. (Replaces the old sphere-cloud box test that over-reported by up to a
  half-extent and the 1 cm vertex-sphere mesh test.)
- **Path:** `BambooMotionScan` samples the motion (≤ 0.5° per joint per check), stops at the
  first Motus contact; play and scrub park on the last clear sample and tint the parts Motus names.
- Allowed contacts: θ1 housing ↔ base tube (the θ1 journal); θ1 housing ↔ L-grip body (the carriage shares the
  joint-1 housing, see below); R-grip jaw plates ↔ strut while gripping.

### Deviation from the ICD URDF: L-grip opened on one side

**L-grip opened on one side to allow side clamping; differs from the ICD URDF.** (Approved by Lassie, 2026-10-08.)
In the ICD layout the L slot (cane axis = jaw z, jaws sliding along x) was walled on both sides: L-grip body
(y 0.012…0.028) and rail (y 0.014) on +y, the arm's base tube (y −0.022…−0.008) on −y — a 20 mm gap for a 14 mm
cane, so the L-grip could only get on/off a cane over a free end. Mirroring R's one-sided layout, the carriage and
rail now sit on the arm side, so the slot is open toward +y:

| part | ICD URDF | now |
|---|---|---|
| L-grip body | 0.020 × 0.016 × 0.026 at y +0.020 (y 0.012…0.028) | 0.020 × 0.012 × 0.026 at y −0.017 (y −0.023…−0.011) |
| L-grip rail | 0.080 × 0.004 × 0.004 at y +0.014 | same box at y −0.0095 (y −0.0115…−0.0075, 0.5 mm off a clamped cane) |
| base tube, jaw plates | unchanged | unchanged |
| joint_1 origin / axes | (0, −0.03, 0), Y | unchanged — kinematics and FK are identical |

The base tube and joint 1 did not have to move: they already lie at y ≤ −0.008 (the θ1 housing at y ≤ −0.0155 for
every θ1, since joint 1 turns about Y), so they do not wall the +y side. The single source of truth is
`tools/bamboo/gen_bamboo_urdf.py` (writes both URDF copies; FK, Motus collision and the viewer's boxes all read
them). `LGrip_IsOpenOnPlusY_ForSideClamping` asserts the open side.

Known colliding nudge: pick `grasp` = **−1.5 mm** (default neck↔strut clearance is 1.0 mm)
→ "Motus stop · Grasp · neck ↔ strut". Place `release` = −10 mm → held strut ↔ ground.

## Run

```bash
cd src/Motus.Viewer
dotnet run --urls http://127.0.0.1:5268
```

Open `http://127.0.0.1:5268/bamboo` (single strut pick/place) or
`http://127.0.0.1:5268/bamboo-truss` (material store → five-member truss frame).

### `/bamboo-truss`: grounded, base-swapping true IK

- **Truss:** five-member bridge frame (rhombus) A–B–D–C, canes `BambooTrussLayout.StrutLength` = **0.25 m**
  (side = height = L, half-span L·√3/2 = 0.217 m): baseL `/` A–B, baseR `_` B–D, diagL A–C, sep `|` B–C,
  diagR D–C. Canes meeting at a node sit in 16 mm lash layers (`LashDz`); A and D sit over anchor posts on pads.
  No hang rod (`IncludePole = false`), no floating mount. Length, stakes, stock and walk live in one `Site`
  (`BambooTrussSites.cs` → `SiteDefaults.Chosen`, switchable with `BambooTrussLayout.Use`).
- **No earth between the anchors:** apart from the A/D anchor pads and posts, nothing on the ground lies
  strictly between A and D in x (`GroundXExtents`, enforced by a test). Both stakes, their pads and the stock
  stand **outboard of A**; inside the span the robot may only clamp canes fixed at both ends. A member is
  placed only when one of its ends is already fixed (A/D, or B/C once triangulated).
- **Why 0.25 m (offline length sweep, reach + Motus search; whole bridge since the PTP planner):**

  | L | baseR from any outboard stake (pure reach) | real planner (Motus) |
  |---|---|---|
  | 0.50 / 0.45 / 0.40 | 0 of 400 random stakes; 0 from post-A | baseL only (previous 0.5 m site) |
  | 0.35 | 0 of 400 random + 3000 near-A stakes; only from post-A (h≈90°, never with baseL) | post-A cannot reach the stock (0 pickable poses) → no chord |
  | 0.30 | reachable (stakes 5 mm outboard of the A pad, h 70–110°) | baseL + baseR + diagL (sep / diagR: no Motus-clear stock grasp / carry from any support) |
  | **0.25** | reachable (same stakes / stock moved in with A by 43.3 mm) | **all five** with PTP, order baseL, baseR, diagL, diagR, sep |
  | 0.22 / 0.20 | — | stock grasp blocked by the pegs / stakes / post A (Cartesian planner) |

  baseR's nearest point is B (x = 0); the closest legal stake is at x = −(L·√3/2 + 0.035). The arm's
  ≈ 0.42 m grip-to-grip reach has to span that plus the clamp-height/z offsets while the same stake also
  reaches the stock behind it — feasible at ≤ 0.30 m. At 0.30 m sep / diagR stay out of reach of a Motus-clear
  carry; at 0.25 m everything is placed from S3 without relays or cradles.
- **Grounded start:** the L-grip starts clamped on **stake S1** (−0.252, clamp y 0.18, z 0.06, heading 90°);
  stake **S3** stands at (−0.252, y 0.21, z −0.04, heading 70°). The stock cane lies flat along z at
  (−0.342, 0.0165) on two narrow **pegs** (`store-peg-1/2`, 0.5 mm seat gap), just outboard of A.
- **Members built: all five** — baseL, baseR, diagL, diagR, sep, every one from stake S3 (stock pick → PTP carry →
  place). diagR goes before sep: with sep standing first, R ends wedged between sep / diagL at C after the place and
  has no Motus-clear way back to the stock (RRT 3 × 1500 fails from q = [81, 90, −5, −88, −81]). Every PTP placement
  must now leave R a Motus-clear park (`R:Park` ends each member cycle); a pose that wedges R is skipped. No cradle /
  relay, no new stakes: cane length + build order were enough. Each member is placed with one end fixed (baseL, diagL:
  A; baseR, diagR: D; sep: B).
- **Invariant:** at every instant ≥ 1 gripper is clamped on a real fixed object (a stake, or a cane fixed at
  both ends) and is the IK base (`MotionKey.Base / BaseWorld / BaseOn`). The other gripper moves only by
  joint IK (`BambooGripKinematics.SolveGrip`, damped least squares on full FK, 5 constraints: grasp centre on
  the object axis + slot axis along it). Grips are accepted within **0.5 mm / 0.5°** (achieved ≈ 1e-7 mm).
  A base swap happens at rest: the newly clamped gripper's FK frame becomes the base, then the old one opens.
- **Phases (PTP, shipped):** `start:Park` → `walk`: `PTP via` / `PTP Grasp` / `Close` R on **stake S3** low (y 0.13) →
  **`swap base L→R`** (own key, at rest) → `L:Open` → `L:PTP off stake-S1` (PTP to top + clear) → `L:PTP via` →
  `L:PTP to stake-S3` → `L:Close stake-S3` → **`swap base R→L`** → `R:Open` → `PTP Retreat` → `R:Park`; then per member
  `PTP via` / `PTP Grasp` / `Close` (R on the stock) → `PTP Lift` → `PTP carry via` (joint via-points / RRT-Connect,
  Motus-checked) → `PTP Place` → `Open` (cane released exactly on its member) → `PTP Retreat` → `R:Park`; then three node
  `walk` blocks on the finished bridge (S3 → baseL B end in two steps: brachiate onto baseR's B end, node transfer with R on
  sep; across B onto baseR with R on sep; back to S3), each R grasp → `swap base L→R` → `L:Open` →
  `L:PTP off X` / `L:PTP via` → `L:PTP to Y` → `L:Close Y` → `swap base R→L` → `R:Open` → `PTP Retreat` → `R:Park`.
  Only canes fixed at both ends are side-clamped (open +y slot). With `Ptp = false` the older Cartesian
  Approach / Lower / Slide phases and the goal-driven brachiation search are still available.
- **Collision:** Motus.NET for every link, both grippers, every mount part (now checked against the
  environment, not only self), the held cane, pads, posts, stakes, rail, placed canes (at their real
  released poses) and self. The only allowed touches are a gripper's jaw plates on what it clamps.
  Cylinder meshes are subdivided along their length (~25 mm rings) so the BVH works for long canes.
- **Scan:** `BambooTrussScan` re-derives everything from the keys (base frame, FK of both grippers, held
  offset from the Close key, released pose from the Open key) and checks every ≤ 0.5° step.
- **Viewer:** the mount is drawn at its full FK pose; an amber ring + label marks **every** clamped gripper
  ("L clamped on stake-S1 (base)", "R clamped on stake-S3 (base)"), both at once when both clamp; a blue ring
  marks the cane in hand. Labels are pushed apart in screen space so "R holds cane" never overlaps the base label. Hold and world for each segment come from the key that ends it (`CycleIndexAt`).
- **World per segment:** start / walk = nothing placed, stock full (the next cane is drawn on the pegs and is a
  Motus obstacle for the planner and the scan); each member cycle then picks it. Base swaps are rest pauses with
  1.2 % of the timeline each so "swap base L→R / R→L" are visible. Pick/place frame labels are drawn small and only
  for the member being built.
- **Play:** `BambooTrussPlayback` dwells 0.35 s at the end of every block (last key of a same-label run),
  keeps time as a double, and never runs past the Motus-verified frontier (time-boxed `StepFor` scan).
- **WASM:** live planning takes ≈ 7 s desktop but minutes in interpreted WASM and cannot yield inside a
  phase, so the page loads the default plan from `Services/BambooTrussDefaultPlan.json` (embedded; keyed by
  `LayoutFingerprint` with numbers rounded to 1e-6 — WASM and desktop `Math` differ in the last ulp — falls back to live planning if stale; the reason is logged to the browser console as `[bamboo-truss] shipped plan not used — …`). A test requires it to be byte-identical to
  live planning; regenerate with `BAMBOO_TRUSS_WRITE_PLAN=1 dotnet test --filter ShippedDefaultPlan`.
- **Not built:** nothing — all five members. Anything a planner run cannot reach is reported, never faked.

### Walking on the bamboo: the `walk` task block (shipped, PTP)

- **Task block:** a `walk` task is a string-identity task like pick/place: `Identity = "walk"`, `Object` = target
  clamp ("placed-baseR", "stake-S3"), one plane `target` at the clamp point on that cane (its parameter is read back
  from the plane), and `Gait`. `BambooTrussMotion.WalkTask(target, f, gait)` builds one; `RunSequence(tasks)` runs
  walk / pick / place blocks in order (BuildAsync hands over to it when a sequence contains walk blocks). The task list
  shows walk blocks as "Walk → target" with a gait selector. The default task list is `BambooTrussMotion.ShippedTasks()`: walk to S3, baseL, baseR, diagL, diagR, sep, then three node walk blocks on the bridge (S3 → baseL B end, across B onto baseR, back to S3).
- **Step (every gait):** R clamps something fixed → `swap base L→R` at rest → L opens and leaves its cane (open side)
  or stake → L clamps the next site → `swap base R→L` at rest → R retreats and parks. One gripper always clamped,
  joints only, FK-exact clamps, only stakes outboard of A and canes fixed at both ends, nothing carried.
  `BambooWalk.Explore` is a BFS over L clamp sites (cane, parameter, side) with deep planner checkpoints per site.
- **Gaits (`BambooWalk.Gaits`):** inchworm (R on L's own cane, L ≤ 7 cm), shuffle (R leads ≤ 13 cm, L closes up one
  3 cm step behind R), brachiation swing (R beside L, L swings ≥ 10 cm to the farthest site), node transfer (L only
  next to a joint, f = ±1, node to node), side-clamp roll (inchworm + re-clamping the same point from the other side).
  Default: node transfer.
- **PTP only:** `BambooTrussPlanner.Ptp = true` — every move is a joint-space point-to-point segment between IK
  waypoints (densely Motus-checked, joint via-points / RRT if the direct segment hits; a backed-off pose may be used
  as a PTP via-point). No Cartesian approach / lower / slide / back-off. Keys are labelled `PTP Grasp`, `PTP Place`,
  `L:PTP to X`, `PTP via`, `PTP carry via`, `PTP Lift`, `PTP Retreat`. The planner's segment check also verifies the
  exact sample points the Motus scan uses (fixes a carry graze "R-grip jaw- ↔ ground-S1" the coarser check missed).
- **Benchmark at 0.30 m (PTP):**

  | Gait | S3 → baseL B end | across B onto baseR | baseR → D end | back to S3 |
  |---|---|---|---|---|
  | node transfer | ✔ 1 step (33.6 cm) | ✔ 1 node transfer (5.4 cm) | ✘ | ✔ 1 step |
  | inchworm / shuffle / swing / roll | ✔ (shared brachiate entry) | ✘ | ✘ | ✔ |

  Winner and default: node transfer. The D end is not reached by any gait and is not in the shipped sequence.
- **0.25 m, whole bridge:** node transfer also uses the new double-fixed sep (R clamps sep beside B). Walks onto sep's
  or diagR's ends (f = ±1) are not reached (23 steps tried, 2 sites); the D end is not in the sequence.
- **Shipped plan (0.25 m, `grounded-ik-8-full-bridge`, 136 keys, all five built, planned live in ≈ 190 s)** — progress:
  walk to S3 0–10.1 %, baseL 10.1–16.4 %, baseR 16.4–27.7 %, diagL 27.7–37.9 %, diagR 37.9–44.9 %, sep 44.9–59.2 %,
  walk (node) → baseL@-1 59.2–71.5 % (brachiate S3 → baseR B end) and 71.5–81.3 % (node transfer, R on sep),
  walk (node) → baseR@-1 81.3–89.6 % (R on sep), walk (node) → stake-S3 89.6–100 %.

## What still differs from the HTML preview

- The planner keeps the HTML's point-model floor heuristics only as IK-branch *preferences*
  (`FloorPenalty`); they never veto a path. Collision verdicts are Motus-only.
- ICD planar IK for play lives in `BambooIcdMotion` (C#); `BambooIcdIk` exposes it as a Motus
  `IInverseKinematics` so `TaskPathValidator` can validate bamboo task paths.
- The grasp plane cannot be driven much lower than −1.5 mm: at −2 mm it is outside the arm's reach.
- Blazor template Counter/Weather pages were removed; Bootstrap assets may remain unused.
