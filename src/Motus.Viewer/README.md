# Motus.Viewer — Blazor WebAssembly Bamboo Arm Viewer

**This is the sole Motus bamboo viewer.** The standalone HTML preview under
`/workspace/bamboo-viewer` (and any sibling Grasshopper PR HTML assets) is
**retired as a product viewer** — kept only as a visual/UX reference. Do not
treat that folder as the shipping UI.

A Blazor WebAssembly app that runs Motus.NET kinematics, collision checking, and
task validation in the browser. The `/bamboo` page ports the look and UX of the
old ICD/LIS HTML preview (pole hang, parallel jaws, θ axes, task cards, scrub)
while Motus.NET remains the source of truth for joint state, tasks, and collision.

## Architecture

```
Browser (WebAssembly)
├── Blazor UI (BambooViewer.razor)       # sliders, tasks, play/scrub, stop-on-hit
├── Motus.NET C# (WASM)
│   ├── bamboo_icd.urdf                  # hung arm: kinematics + collision boxes (generated)
│   ├── BambooIcdCell                    # robot model + CollisionScene (pole, strut, ground, mount)
│   ├── RobotMeshCollisionChecker        # exact narrow phase, FindContacts → named hit pairs
│   ├── BambooMotionScan                 # samples the motion, first hit / last clear sample
│   └── BambooIcdMotion / BambooIcdIk    # ICD planar IK + motion keys (+ Motus IInverseKinematics)
└── Three.js (js/viewer.js)              # draw only, from the cell description C# hands it
```

**Key principle:** Three.js only draws. Joint angles, gripper openings, the strut
pose (Motus FK), task frames, and collision status are computed in C# and pushed via
`initThreeJs(cell)` / `setBambooPose` / `setBambooFrames`. There is no JS collision code.

## Frame convention

| Layer | Up axis | Notes |
|-------|---------|-------|
| Three.js viewer | **Y-up** | pole at `y = 0.40`, segments along local −Y |
| Motus.NET | **Z-up** | `Motus = Rx(+90°) · viewer`, i.e. viewer `(x, y, z)` → Motus `(x, −z, y)` |

`bamboo_icd.urdf` (generated by `tools/bamboo/gen_bamboo_urdf.py`) hangs the arm from a
fixed `pole_hang` joint (`xyz 0 0 0.40`, `rpy π/2 0 π/2`) so every URDF link frame *is* the
matching Three.js group (mount, j1…j5, jaw). Tests assert Motus FK == the drawn chain to 1e-9 m.
Task planes → Motus TCP frames: `BambooIcdMotion.PlaneToMotusFrame` (rotation `Rx(90° + pitch)`).

## Collision (what Motus checks)

- **Robot:** the URDF's own `<collision>` boxes per link — θ housings, link tubes, neck,
  R-grip carriage/rail/jaw plates (plates moved to the current gR opening). viewer.js builds its
  boxes from the same list, so drawn == collided.
- **Scene (`CollisionScene`):** support pole (Three.js-tessellated cylinder mesh), strut (mesh),
  ground slab (box, top at y = 0), fixed mount parts (base tube, L-grip body/rail/jaws at gL).
- **Self:** every part pair except directly-jointed links (`selfCollisionMinLinkGap = 2`).
- **Strut physics:** it rests where the pick object lies (grasp plane un-nudged origin);
  is captured at its real jaw-local offset when the jaws close (attached body, checked against
  scene + all links); stays where released. Only the two R-grip jaw plates may touch it while
  gripping. Closed jaws that would not enclose it → "grasp misses strut", it stays on the ground.
- **Narrow phase:** exact OBB–OBB (SAT), triangle–OBB (SAT), closest-point sphere–triangle,
  mesh vs half-space. (Replaces the old sphere-cloud box test that over-reported by up to a
  half-extent and the 1 cm vertex-sphere mesh test.)
- **Path:** `BambooMotionScan` samples the motion (≤ 0.5° per joint per check), stops at the
  first Motus contact; play and scrub park on the last clear sample and tint the parts Motus names.
- Allowed contacts: θ1 housing ↔ base tube (the θ1 journal); θ1 housing ↔ L-grip body (the carriage shares the
  joint-1 housing, see below); R-grip jaw plates ↔ strut while gripping.

### Deviation from the ICD URDF: L-grip opened on one side

**L-grip opened on one side to allow side clamping; differs from the ICD URDF.** (Approved by Lassie, 2026-10-08.)
In the ICD layout the L slot (cane axis = jaw z, jaws sliding along x) was walled on both sides: L-grip body
(y 0.012…0.028) and rail (y 0.014) on +y, the arm's base tube (y −0.022…−0.008) on −y — a 20 mm gap for a 14 mm
cane, so the L-grip could only get on/off a cane over a free end. Mirroring R's one-sided layout, the carriage and
rail now sit on the arm side, so the slot is open toward +y:

| part | ICD URDF | now |
|---|---|---|
| L-grip body | 0.020 × 0.016 × 0.026 at y +0.020 (y 0.012…0.028) | 0.020 × 0.012 × 0.026 at y −0.017 (y −0.023…−0.011) |
| L-grip rail | 0.080 × 0.004 × 0.004 at y +0.014 | same box at y −0.0095 (y −0.0115…−0.0075, 0.5 mm off a clamped cane) |
| base tube, jaw plates | unchanged | unchanged |
| joint_1 origin / axes | (0, −0.03, 0), Y | unchanged — kinematics and FK are identical |

The base tube and joint 1 did not have to move: they already lie at y ≤ −0.008 (the θ1 housing at y ≤ −0.0155 for
every θ1, since joint 1 turns about Y), so they do not wall the +y side. The single source of truth is
`tools/bamboo/gen_bamboo_urdf.py` (writes both URDF copies; FK, Motus collision and the viewer's boxes all read
them). `LGrip_IsOpenOnPlusY_ForSideClamping` asserts the open side.

Known colliding nudge: pick `grasp` = **−1.5 mm** (default neck↔strut clearance is 1.0 mm)
→ "Motus stop · Grasp · neck ↔ strut". Place `release` = −10 mm → held strut ↔ ground.

## Run

```bash
cd src/Motus.Viewer
dotnet run --urls http://127.0.0.1:5268
```

Open `http://127.0.0.1:5268/bamboo` (single strut pick/place) or
`http://127.0.0.1:5268/bamboo-truss` (material store → Warren truss over a pit). A bottom **timeline** shows one
block per task (pick / place / retreat / walk / swap / park-relay, colour-coded), the playhead, the current % and phase;
click or drag the track to scrub, click a block to jump to its start; Play/Pause and Reset sit on its left.

### `/bamboo-truss`: Warren truss over a U-shaped pit (grounded, base-swapping true IK)

- **Truss (Lassie's redesign):** classic three-triangle Warren truss, all triangles equilateral (60°), panel
  **P = 0.30 m**: bottom chord A–M (`AM`), M–D (`MD`); diagonals A–T1 (`AT1`), T1–M (`T1M`), M–T2 (`MT2`),
  T2–D (`T2D`); top chord T1–T2 (`T1T2`). Pin support at A, roller at D. **Every member axis lies in one vertical
  plane** (z = `PlaneZ` = 0.11): no lash layers / offsets any more.
- **Node connectors:** a 30 mm cube (`HubHalf` = 15 mm) at every node, drawn and a Motus obstacle. A and D's
  connectors sit on the support columns from the start; M / T1 / T2 appear with the first member that reaches them
  (`HubObjects`, same rule in planner, scan and viewer). Every cane = **P − 2 × node gap** = 0.30 − 2 × 0.03 =
  **0.24 m** (`Site.Gap`), identical for all members, so cane ends stop 30 mm short of the node centre (≥ 4.5 mm
  clear of the cube) and canes never touch each other.
- **Pit:** ground surfaces at support level (top y = 0) outside A and D (`ground-W`, `ground-E`, 0.55 m wide,
  ±0.45 m across the plane); between them a U-section pit 0.576 m wide (edges 12 mm inboard of the A / D column
  axes) and **0.25 m deep**: two vertical walls (`pit-wall-W/E`) and a floor (`pit-floor`). All are Motus boxes and
  drawn in the viewer. There is no earth inside the span: the robot can only clamp the anchor columns or members.
- **No stakes.** S1 / S3 and every other clamp stake are gone. The only fixed clamp supports are the **anchor
  columns** under A and D (14 mm, from the ground up to the connector; `anchor-A`, `anchor-D`). The robot starts
  with its L-grip clamped on `anchor-A` (clamp height 0.09 m, heading 60°). With the connector above the column has
  no free top, so the L-grip leaves it sideways out of its open (+y) side (`L:PTP off anchor-A`).
- **Fixed members (walkable):** a member may be clamped once both its end nodes belong to a **rigid, anchored
  subframe**: a cluster seeded by a closed triangle of placed members, grown by every node tied to it by two placed
  members, merged when clusters share two nodes, and counted only if it contains A or D (`AnchoredRigidClusters`,
  `FixedBothEnds`). A lone cantilevered member is not fixed; the closed triangle A–M–T1 hinged at A is. A member is
  placed with at least one end on an existing node (A / D or a node a placed member reaches; `ExistingNodes`).
- **Stock:** the cane lies flat in the truss plane on two pegs 0.12 m outboard of A, outside the pit.
- **Invariant:** at every instant ≥ 1 gripper is clamped on a real fixed object (an anchor column, or a member
  fixed into the structure) and is the IK base (`MotionKey.Base / BaseWorld / BaseOn`). The other gripper moves only
  by joint IK (`BambooGripKinematics.SolveGrip`). Grips are accepted within **0.5 mm / 0.5°**. Base swaps happen at
  rest with their own labelled key. PTP only: joint-space moves (via-points / RRT-Connect), every segment
  Motus-checked at the scan's sample fractions (graze fix); never walks while carrying; no hang rod.
- **Collision:** Motus.NET for every link, both grippers, every mount part, the held cane, ground surfaces, pit
  walls and floor, anchor columns, connectors, stock pegs, placed canes and self. The only allowed touches are a
  gripper's jaw plates on what it clamps.
- **Scan / playback / WASM:** unchanged — `BambooTrussScan` re-derives everything from the keys; the page loads the
  embedded `Services/BambooTrussDefaultPlan.json` keyed by the 6-decimal `LayoutFingerprint`; regenerate with
  `BAMBOO_TRUSS_WRITE_PLAN=1 dotnet test --filter ShippedDefaultPlan`.

### Walking on the bamboo: the `walk` task block (shipped, PTP)

- **Task block:** a `walk` task is a string-identity task like pick/place: `Identity = "walk"`, `Object` = target
  clamp ("placed-AM", "anchor-A"), one plane `target` at the clamp point on that cane (its parameter is read back
  from the plane), and `Gait`. `BambooTrussMotion.WalkTask(target, f, gait)` builds one; `RunSequence(tasks)` runs
  walk / pick / place blocks in order (BuildAsync hands over to it when a sequence contains walk blocks). The task list
  shows walk blocks as "Walk → target" with a gait selector. `LandTask(member)` instead chooses a clamp site from which
  that member can actually be built. The shipped Warren sequence has four targeted landings: T1–T2, M–D, the T2–D
  relay park in T1/z+, and the final T2–D placement. `ShippedTasks()` reads the searched sequence from the shipped plan
  or runs a build search when the layout changes.
- **Step (every gait):** R clamps something fixed → `swap base L→R` at rest → L opens and leaves its cane (open side)
  or anchor column → L clamps the next site → `swap base R→L` at rest → R retreats and parks. One gripper always clamped,
  joints only, FK-exact clamps, only anchor columns and canes fixed into the anchored subframe, nothing carried.
  `BambooWalk.Explore` is a BFS over L clamp sites (cane, parameter, side) with deep planner checkpoints per site.
- **Gaits (`BambooWalk.Gaits`):** inchworm (R on L's own cane, L ≤ 7 cm), shuffle (R leads ≤ 13 cm, L closes up one
  3 cm step behind R), brachiation swing (R beside L, L swings ≥ 10 cm to the farthest site), node transfer (L only
  next to a joint, f = ±1, node to node), side-clamp roll (inchworm + re-clamping the same point from the other side).
  Default: node transfer.
- **PTP only:** `MotionConstraints.PointToPointOnly` — every move is a joint-space point-to-point segment between IK
  waypoints (densely Motus-checked, joint via-points / RRT if the direct segment hits; a backed-off pose may be used
  as a PTP via-point). No Cartesian approach / lower / slide / back-off. Keys are labelled `PTP Grasp`, `PTP Place`,
  `L:PTP to X`, `PTP via`, `PTP carry via`, `PTP Lift`, `PTP Retreat`. The planner's segment check also verifies the
  exact sample points the Motus scan uses.

### Motion rules, shared collision check, reach map, scene check (`/bamboo-truss`)

- **`MotionConstraints`** — one profile (PTP-only, one clamped base, swaps at rest, fixed-member rule, park after
  place, clearance margin, sample resolutions). `BambooTrussPlanner(cell, constraints?)` and `BambooTrussScan(...,
  constraints?)` read it; `Validate()` rejects rules the planner cannot honour (a clearance margin needs distance
  queries Motus does not have yet, so it must be 0).
- **`BambooTrussCollision`** — the single collision check: environment, allowed jaw contacts, pose contacts, and the
  canonical sample points of a segment (n = ⌈1.5 · max(Δq / 0.5°, Δjaw / 0.25 mm)⌉, fractions s/n). The planner's
  verify pass checks these points (plus finer ones); the scan checks exactly these points (mapped through the playback
  easing). Property test: any segment the planner accepts, the scan accepts.
- **`BambooReachMap`** — for a clamp site (`AnchorSites`, `CaneSites`: base-gripper frame on a column or a cane, any
  heading / roll), does the free gripper reach a target line (`Stock()`, `PlaceOf(member)`, a parked pose) by IK,
  optionally with a Motus-clear pose (`Collision`)? `Query(site, line)`, `Matrix(sites, lines)` (parallel,
  deterministic), sound distance prefilter `MaxReachM`.
- **`BambooSceneCheck.Run`** — before planning (`BambooTrussMotion.SceneCheckFirst`): per member, the number of sites
  reaching the stock, the place, and both; if none reaches both, the shortest relay chain over connector park poses
  (and all single-park options). Optimistic about build order, so a failure means "cannot be built from this layout"
  and planning is refused with those numbers. Warren: 7/7, T2–D needs a relay (304 sites × 28 lines, ≈ 9 s IK-only).

## What still differs from the HTML preview

- The planner keeps the HTML's point-model floor heuristics only as IK-branch *preferences*
  (`FloorPenalty`); they never veto a path. Collision verdicts are Motus-only.
- ICD planar IK for play lives in `BambooIcdMotion` (C#); `BambooIcdIk` exposes it as a Motus
  `IInverseKinematics` so `TaskPathValidator` can validate bamboo task paths.
- The grasp plane cannot be driven much lower than −1.5 mm: at −2 mm it is outside the arm's reach.
- Blazor template Counter/Weather pages were removed; Bootstrap assets may remain unused.

### Structure graph and build search (P4)

- `BambooStructureGraph`: nodes (with connectors), members as edges, anchors (nodes with a clamp column). `ExistingNodes`,
  `Frontier` (members that can be started), `AnchoredRigidGroups`, `FixedNodes`, `Fixed` (walkable members: both ends in
  one rigid group that reaches an anchor). `BambooTrussLayout.FixedBothEnds` & co. delegate to it.
- `BambooBuildSearch.Run(cell)`: depth-first over build states. At each state the frontier members are ranked by the
  cheapest mode the reach map allows with the *real* fixed set of that state — direct from where the arm stands, one
  targeted-landing walk, or one relay (candidates: the scene check's single-park options, 11 for T2–D) — far members
  first. Every choice is confirmed with the real planner (Motus-clear, PTP) and rolled back, random stream included,
  if it or anything after it fails. The default task list (`BambooTrussMotion.ShippedTasks`) is the search result:
  the build-time plan carries it (`PlanCache.Tasks`); on a layout change the search runs live.
- Planner: a deep checkpoint now also rewinds the RRT random stream, so a tried-and-abandoned branch leaves no trace
  and re-planning the searched sequence is identical. Each checkpoint retains its own random history, so walk BFS can
  restore older and newer branches in any order. A placement is also rejected when the released cane itself
  (jaw FK ∘ held offset — grasp and place residuals add) is off its design pose by more than 0.5 mm / 0.5°.
- Shipped (`warren-pit-3-search`): AT1 → T1M → AM → land → T1T2 → land → MD → MT2 → land → park T2D in T1/z+ →
  land → re-grasp → T2D. 7/7, 4 walks, 8 base swaps, one relay.
- Search budgets are deterministic: at most 40 rejected choices and 1000 total planner confirmations by default.
  An incomplete result retains the longest confirmed prefix and its stop reason. `ShippedTasksSource`,
  `ShippedTasksDiagnostics` and `ShippedTasksError` expose a failed derivation; graph-order fallback tasks remain
  editable but `BuildAsync` reports the failure instead of playing them as a finished default plan. A cell-unavailable
  fallback is invalidated when `UseCell` binds the viewer cell. All editable task fields participate in shipped-plan
  cache identity.
